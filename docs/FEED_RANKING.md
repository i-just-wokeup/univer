## 2. 홈 피드 — 밴드 구조

`supabase/migrations/20260904150000_feed_follow_band_and_author_cap.sql`

커서는 `(band, rank)`. 낮은 밴드부터, 밴드 안에서는 `rank` 내림차순.

| 밴드 | 조건 | rank(정렬 기준) |
|---|---|---|
| 0 | 안 봤음 AND (크루 OR 팔로우) AND 작성자별 최신 2개 이내 | `created_at` (최신순) |
| 1 | 안 봤음 AND **48시간 이내** | `created_at` (최신순) |
| 2 | 안 봤음 AND 30일 이내 | 핫스코어 |
| 3 | 봤음 AND 7일 이내 | **seed 해시(무작위)** |
| 4 | 나머지 전부 | **seed 해시(무작위)** |

**핫스코어(밴드 2)**

```
(1 + 좋아요 + 댓글×2) × 0.5^(글나이_일 / 반감기_5일)
```

**공통 제외**: 삭제된 글, 차단 양방향, 본인 글

**인자와 기본값**

| 인자 | 기본값 | 의미 |
|---|---|---|
| `p_seed` | — | 무작위 섞기 씨앗. 새로고침마다 새로 생성 |
| `p_limit` | 20 | 한 페이지 개수 |
| `p_half_life_days` | 5 | 밴드 2 반감기 |
| `p_fresh_hours` | **48** | 밴드 1 기준 (2026-09-11에 6→48) |
| `p_recent_days` | 30 | 밴드 2 기준 |
| `p_reshow_days` | 7 | 밴드 3 기준 |

**작성자 상한**: 밴드 0은 한 사람당 최신 2개까지. 3번째부터는 밴드에서 빠져 원래 자리(밴드 1·2·4)로 내려간다. 삭제가 아니라 밀어내기.

**앱이 밴드 숫자를 판단하는 곳**: `components/home/HomeFeedList.tsx` 한 곳뿐. `band >= 3`이면 "모두 열람했습니다" 마커를 넣는다. 밴드 개수나 의미를 바꿀 때 반드시 같이 확인할 것.

## 3. 탐색

`supabase/migrations/20260904140000_explore_base_score_and_creator_boost.sql`

```
점수 = (1 + 좋아요 + 댓글×2)
     × 0.5^(글나이_시간 / 반감기_120시간)
     × (승격·공식 계정이면 1.5배)
```

| 인자 | 기본값 |
|---|---|
| `p_limit` | 30 (앱은 24+1) |
| `p_offset` | 0 |
| `p_half_life_hours` | 120 (=5일) |
| `p_creator_boost` | 1.5 |

**대상**: 전체공개 + 미디어 있는 글, 본인·차단 제외

- **나이 제한 없음** — 136일 된 글도 목록에 들어간다(점수가 낮아 아래일 뿐)
- **본 글을 걸러내지 않음** — 홈에서 본 글이 탐색에 또 나온다
- **작성자 상한 없음** — 한 사람이 상단을 독점할 수 있다(홈에는 있음)
- **페이지네이션이 `offset` 기반** — 점수가 시간에 따라 변하므로 스크롤 중 순서가 바뀌면 같은 글이 두 번 나오거나 건너뛴다. 홈은 커서 방식인데 탐색만 옛 방식. **알려진 결함.**

**연속 화면**: `usePostSequence.ts` 가 탐색 캐시(`explore/page-cache.ts`, TTL 5분)를 그대로 이어 쓴다. 별도 정렬이 없다.

## 4. 열람 기록

`post_impressions (user_id, post_id, seen_at)`

- 기록 조건: 화면의 **60% 이상 + 2초** (`HomeFeedList.tsx`, `lib/constants/feedViewability.ts`)
- 저장: `ignoreDuplicates: true` → **다시 봐도 아무 것도 안 바뀐다.** `seen_at`은 처음 본 시각에 고정
- 피드 함수는 `seen_at`을 쓰지 않고 `exists()`로 봤나/안 봤나만 본다 → **가진 정보를 버리는 중**
- 도달(reach) = 이 테이블의 고유 계정 수. 인사이트 화면이 이미 보여준다(`features/metrics/api.ts`)

## 6. 확정된 변경 계획 (2026-09-11 결정, 미구현)

### A. 새 글 도달 보장 — 넣기로 함 (🟡 1단계만 적용됨)

> **2026-09-11 적용**: 아래 설계 대신 **밴드 1의 창을 6→48시간으로 넓히는 것만** 먼저 했다(`20260911100000_feed_fresh_window_48h`).
> 밴드 1에 "안 봤음"이 이미 있어 그것만으로 "안 본 사람에게 이틀간 계속 보인다"가 된다. 설정 테이블도 도달 수 계산도 필요 없었다.
> 아래의 **도달 수 기반 보장·크리에이터 차등**은 이 변경의 효과(평균 도달 6.4명이 오르는지)를 며칠 본 뒤 판단한다.

밴드 1의 조건을 **시간 → 도달 수**로 바꾼다.

```
지금:  올린 지 6시간 이내면 밴드 1
바꾸면: 아직 N명에게 도달 못 했고 AND 올린 지 48시간 이내면 밴드 1
```

새벽에 올려 아무도 못 본 글이 그대로 묻히는 걸 막는다. 시간 상한을 같이 두지 않으면 도달이 안 늘어 맨 위에 영구히 박힌다.

| 대상 | 보장 도달 | 보장 기간 |
|---|---|---|
| 일반 | 최근 7일 활동자의 **60%** (지금 8명) | 48시간 |
| 크리에이터(승격·공식) | 최근 7일 활동자의 **90%** (지금 12명) | 72시간 |

**절대값이 아니라 비율인 이유**: 최근 7일 앱을 연 사람이 13명이라 "15명 보장"은 물리적으로 불가능하다. 비율이면 사람이 늘 때 자동으로 늘어난다.

### B. 묻힌 글 구제 — 약하게만

밴드 2(안 본 글) 안에서 **도달 적은 글에 가산점**. 새 밴드를 만들지 않는다.
어차피 보여줄 글의 순서만 바꾸는 것이라 중복 위험이 없다.
세기는 "한 페이지에 한 개꼴"로 약하게. 60일 초과 글은 대상에서 제외(볼 사람이 없던 시절 글).

### C. `feed_settings` 테이블

값을 함수 인자로 빼면 **앱이 값을 넘겨야 해서 조정할 때마다 OTA가 필요하다.** 설정 테이블을 함수가 직접 읽으면 DB에서 숫자 하나만 바꿔도 다음 새로고침부터 반영된다.

| 설정 | 초기값 |
|---|---|
| `reach_guarantee_ratio` | 0.60 |
| `reach_guarantee_ratio_creator` | 0.90 |
| `guarantee_hours` | 48 |
| `guarantee_hours_creator` | 72 |
| `active_window_days` | 7 |
| `rescue_max_age_days` | 60 |
| `rescue_strength` | 약하게 |

나중에 `/admin`에 입력칸을 만들면 직접 조정할 수 있다.

**확인용 지표도 같이 필요**: 어제 글의 보장 달성률 / 평균 도달 / 보장 못 채우고 만료된 글 수. 없으면 숫자를 감으로 바꾸게 된다.

## 7. 논의했지만 **안 하기로** 한 것

다시 꺼내지 않기 위해 이유와 함께 남긴다.

| 안 하는 것 | 이유 |
|---|---|
| 탐색에서 본 글 제외 | 글이 117개뿐이라 걸러내면 탐색이 빈다. 인스타는 글이 수억 개라 자연히 안 겹치는 것 |
| 점수를 개수 → 도달당 비율로 | 사람이 적던 시절 글이 영원히 이긴다(넉 달 전 글이 1·2·4위). 나이 상한과 반드시 같이 가야 함. 글이 늘면 재검토 |
| 탐색 나이 상한 30일 | 위와 같은 이유로 보류. 비율 점수를 안 쓰면 굳이 필요 없음 |
| 탐색 무한 스크롤(본 글 재투입) | 글 117개에 무한 스크롤을 붙이면 중복이 반드시 생긴다. 글이 수천 개 되면 재검토 |
| 탐색 격자를 고정 순서로 | **한 번 제안했다가 철회.** 인스타 탐색은 열 때마다 바뀐다. 격자도 섞는 게 맞다 |
| 크리에이터 노출 배수(1.5배) 유지 | 배수는 제로섬이라 크리에이터가 늘면 혜택이 저절로 사라진다. "도달 보장"으로 대체 |
| 팔로워 공지(브로드캐스트) | 크리에이터 혜택으로 약하다고 판단 |
| 공개 프로필 주소 `/u/닉네임` | 앱이 아직 비공개 테스트라 스토어 주소가 없다. 데려와도 설치를 못 한다. **프로덕션 출시 후 재검토** |
| `/p/` 공유 페이지 버튼 → 스토어 | 같은 이유. 출시 후 |

**보류 중인 알려진 결함** (고쳐야 하지만 이번 범위 아님)

- 탐색 `offset` 페이지네이션 → 커서로 바꿔야 함
- 탐색에 작성자 상한 없음 → 크리에이터가 늘면 도배 가능
- 탐색 크리에이터 가산점 1.5배가 **승격 계정 1명 기준**으로 맞춰진 값 (현재 2명)
- `/p/` 공유 페이지가 6월 보라색(`#7c3aed`)을 그대로 씀 — 앱은 7/31에 모노로 전환
- 저장(`bookmarks`)·영상 완주율(`reel_watch_events`)을 기록하면서 순위에 안 씀

## 8. 외부 참고 (2026-09-11 조사)

**틱톡** — 공식: "팔로워 수도, 예전에 잘 된 영상이 있었는지도 추천의 직접적 요소가 **아니다**". 새 영상을 소수에게 먼저 보여주고 반응에 따라 확대하는 구조(구체적 배치 크기는 비공식 추정치뿐). "같은 크리에이터 영상 두 개가 연속으로 나오지 않는다". 관련 없어 보이는 영상을 **의도적으로** 섞어 새 크리에이터 발견을 유도한다. 유출 문서(`TikTok Algo 101`, 회사가 진본 확인)의 목표 4개에 **크리에이터 가치**가 명시됨.

**X(트위터)** — 2023년 코드 공개. 팔로우 50% / 비팔로우 50%를 **구조로 할당**(점수 경쟁이 아님). 순위 계산 후 규칙 적용: 작성자 다양성, 콘텐츠 균형, 피드백 피로도, 사회적 증거.

**인스타그램** — 2010~2016년 피드는 **순수 최신순**(알고리즘 없음). 전환 근거는 "사람들이 글의 70%를 놓친다". 탐색의 전신 "Popular"(2010~2012)는 좋아요 순 하나로 **전원 동일 화면**이었고 관심사를 못 맞춰 폐기. 2018년 공개 신호는 관심·최신·관계 3개뿐. 현재는 수만 → 500 → 150 → 50 → 25 단계 축소 구조.

**초기 부트스트랩** — 레딧은 창업자들이 가짜 계정으로 직접 글을 올렸고, 옐프·쿼라는 직원이 콘텐츠를 썼다. 유튜브는 수동 큐레이션 → 인기순 → 알고리즘 순으로 옮겼다.

**우리 상황과의 차이**: 인스타가 푼 문제는 "너무 많아서 못 봄"(70% 놓침)이고, 우리 문제는 "너무 적어서 다 봄"(안 본 글 0개)이다. 정반대다. 활동 사용자가 22명인 동안에는 크리에이터가 받을 수 있는 최대 도달도 22명이라, **알고리즘으로 늘릴 수 있는 상한이 이미 거의 찼다.**
